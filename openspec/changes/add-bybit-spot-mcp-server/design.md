# Design

## Context

Проект `mcp-bybit` сейчас пуст (только служебные файлы OpenSpec). Образец — `mcp-moex` (`/media/alexey/DATA/Projects/Python/mcp-moex`): async MCP-сервер на Python (`mcp` SDK, `httpx`, `pydantic`), с тонким HTTP-клиентом биржи, резолвером тикера, модулем чистой аналитики и точкой входа `server.py`, которая регистрирует инструменты через `@server.tool(...)`. Мотивация и границы изменения — см. `proposal.md`.

Bybit v5 REST API (`https://api.bybit.com`, публичные market-эндпоинты, без аутентификации) отличается от ISS в нескольких местах, важных для реализации:
- Конверт ответа: `{"retCode": 0, "retMsg": "OK", "result": {...}, "time": 1690000000000}`. `retCode != 0` — доменная ошибка биржи (например `170121` — неизвестный символ), а не транспортная.
- `GET /v5/market/instruments-info?category=spot` — справочник пар: `symbol`, `baseCoin`, `quoteCoin`, `status` (только `Trading` торгуется).
- `GET /v5/market/tickers?category=spot&symbol=...` — текущая цена: `lastPrice`, `bid1Price`, `ask1Price`, `price24hPcnt`, `highPrice24h`, `lowPrice24h`, `volume24h`, `turnover24h`. Нет пометки времени на уровне тикера — только общее `time` в конверте ответа.
- `GET /v5/market/kline?category=spot&symbol=...&interval=...&start=&end=&limit=` — свечи: `interval` — коды `1,3,5,15,30,60,120,240,360,720,D,W,M` (минуты либо день/неделя/месяц), максимум 1000 свечей за вызов, список отсортирован по убыванию `startTime` (сначала новые).

## Goals / Non-Goals

**Goals:**
- Дать конкретный, воспроизводимый план реализации: структура пакета, модули, их обязанности и то, как переиспечь движок аналитики из `mcp-moex` почти без изменений.
- Зафиксировать технические решения, которые спеки намеренно оставляют как поведенческий контракт, а не как реализацию: набор интервалов истории, алгоритм пагинации, стратегию ретраев и кэша, схему ошибок.

**Non-Goals:**
- Категории linear/inverse/option, funding rate, open interest, стакан, лента сделок, режим расписания (watch/SQLite) — вне рамок, см. `proposal.md`.
- Аутентификация и приватные эндпоинты Bybit.

## Decisions

### Структура пакета — зеркалит `mcp-moex`
```
src/mcp_bybit/
  __init__.py
  errors.py       # BybitError и подклассы (аналог errors.py)
  bybit.py        # тонкий async-клиент (аналог iss.py): GET, ретраи, кэш, конверт retCode/retMsg
  resolver.py     # symbol -> Instrument(symbol, base_coin, quote_coin, status) через instruments-info
  models.py       # pydantic-модели параметров и результатов инструментов
  server.py       # точка входа: регистрация 6 инструментов, CLI, транспорт
  tools/
    __init__.py
    search.py     # search_symbols
    price.py      # get_current_price
    history.py    # get_price_history
    analytics.py  # тонкие обёртки над analytics/*, валидация входа
  analytics/
    __init__.py
    series.py     # Bar/Series — перенос без изменений (общая математика по OHLC)
    stats.py      # перенос с одной правкой: ANNUALIZATION_FACTORS для 1d/1w/1M вместо day/week/month
    core.py       # перенос с правкой заметок (см. ниже) и вызовов stats/series
    text.py       # перенос форматирования, даты в UTC вместо MSK
    build.py       # сборка результата инструмента из core
tests/            # структура и подход как в mcp-moex (см. Migration Plan)
scripts/
  smoke_client.py # аналог: реальный вызов Bybit по всем 6 инструментам
```

**Почему.** `mcp-moex` уже показал, что такое разделение (тонкий HTTP-клиент / резолвер / чистая аналитика / инструменты-обёртки / сервер) даёт: аналитику без сети и без состояния (легко тестировать), резолвер как единственное место, где решается "что такое этот тикер", и сервер как единственное место, где живёт MCP-протокол. Альтернатива — один плоский модуль на инструмент со своей HTTP-логикой — была отклонена, т.к. дублировала бы ретраи/кэш/резолвинг в трёх местах.

### `resolver.py` устроен проще, чем в mcp-moex
Так как поддерживается только `category = spot`, резолверу не нужно определять класс актива и площадку — только: (1) существует ли `symbol` среди spot-инструментов, (2) его `status`, (3) `base_coin`/`quote_coin`. Реализация: один запрос `instruments-info?category=spot&symbol=<SYMBOL>` (Bybit принимает точный тикер как фильтр, без листания всего справочника), TTL-кэш в памяти (аналог `REFERENCE_TTL` — 6 часов), т.к. состав торгуемых пар меняется редко. `search_symbols`, наоборот, должен видеть весь список пар сразу — для него отдельный кэшируемый вызов `instruments-info?category=spot` без `symbol` (весь справочник, ~2000+ пар, укладывается в один ответ, пагинация Bybit для spot не нужна согласно документации).

**Альтернатива, отклонена:** резолвить через один и тот же полный список для `get_current_price`/`get_price_history` — проще по коду, но означает всегда тянуть весь справочник (лишний трафик и задержка) там, где нужен один тикер.

### Интервалы истории — суженный человекочитаемый enum
Bybit принимает интервалы в минутах и кодах `D/W/M`. Инструменту отдаём enum `15m, 1h, 4h, 1d, 1w, 1M` (по умолчанию `1d`) — подмножество, покрывающее типичные горизонты анализа, вместо всех 13 кодов Bybit (`3m`, `5m`, `30m`, `2h`, `6h`, `12h` практически не нужны агенту и раздували бы схему). Отображение на коды Bybit: `{"15m": "15", "1h": "60", "4h": "240", "1d": "D", "1w": "W", "1M": "M"}`.

**Почему не пробрасывать все коды Bybit напрямую:** это протекающая абстракция (агенту пришлось бы знать, что `"60"` значит час), а описание инструмента и так должно объяснять интервалы по-русски.

### Пагинация `get_price_history`
Bybit отдаёт максимум 1000 свечей за вызов, отсортированных по убыванию `startTime`. Алгоритм: запрашивать с `end = date_till` (конец окна в мс), после каждого ответа брать минимальный `startTime` среди полученных свечей и делать следующий запрос с `end = min_startTime - 1`, пока не будет достигнут `start = date_from` в мс или Bybit не вернёт пустой список. Собранные свечи объединяются и сортируются по возрастанию `begin` перед подсчётом `summary`. Ограничение на общий объём — как в спеке: если по интервалу и периоду ожидается больше 5000 свечей (оценивается по разнице дат и длительности свечи до похода в сеть), вызов сразу завершается ошибкой без обращения к бирже.

### Ретраи и кэш в `bybit.py` — перенос `iss.py` почти без изменений
Тот же паттерн: `httpx.AsyncClient(trust_env=False)`, ретраи на `429`/`5xx`/сетевых ошибках с экспоненциальной паузой, TTL-кэш в памяти по ключу (путь + отсортированные параметры). Дополнительно: клиент разбирает конверт `retCode`/`retMsg` — `retCode == 0` возвращает `result`, иначе поднимает `BybitApiError(retCode, retMsg)` (кроме `170121` — неизвестный символ, который транслируется в доменную ошибку `SymbolNotFound`, а не в общую `BybitUnavailable`). TTL котировок: 5 секунд (короче, чем `QUOTE_TTL = 10` в ISS, т.к. у крипты нет 15-минутной задержки и цена меняется быстрее — короткий кэш просто гасит всплеск одинаковых вызовов, не создавая ощутимого расхождения с реальностью).

### Перенос модуля аналитики — с тремя точечными правками
Модули `series.py` и большая часть `core.py`/`stats.py`/`text.py` из `mcp-moex` переносятся как есть (математика волатильности/просадки/корреляции/беты не зависит от класса актива). Три места меняются:
1. `ANNUALIZATION_FACTORS`: `{"1d": 365, "1w": 52, "1M": 12}` вместо `{"day": 252, "week": 52, "month": 12}` — крипта торгуется 24/7, торговых дней в году 365, а не 252.
2. Заметки (`DIVIDENDS_NOTE`, `BOND_NOTE`, `BENCHMARK_NOTE`, `CURRENCY_NOTE` в `core.py`): заменяются на формулировки для крипты — нет дивидендов/купонов (заметка про комиссии и отсутствие учёта наград/эйрдропов), нет отдельного случая "облигация", `CURRENCY_NOTE` переиспользуется почти как есть (только "валюта котировки" → "котируемая монета"), `BENCHMARK_NOTE` заменяется на пояснение, что эталон (например `BTCUSDT`) сам является рискованным активом, а не безрисковым индексом — в отличие от IMOEX, аналогии "индекс полной доходности" у крипты нет.
3. Даты/время: UTC вместо часового пояса Москвы (`MSK` → `UTC`, без сдвига `+03:00`).

Требование признака незакрытой свечи (`partial = true` у последней) сохраняется как есть, только "сегодня по Москве" (`today()` в `server.py`) заменяется на "сегодня по UTC".

### Формат ошибок и коды Bybit
`retCode` из ответа Bybit никогда не попадает в текст ошибки как голое число — он транслируется в один из доменных классов `errors.py` (`SymbolNotFound`, `UnsupportedCategory`, `BybitUnavailable`, `InvalidArgument`, `TooManyCandles`) с русским текстом, объясняющим, что делать. Это то же решение, что в `mcp-moex` (`IssUnavailable` и соседние классы), перенесённое на другой набор кодов биржи.

## Risks / Trade-offs

- **[Риск]** Один и тот же `symbol` (например `BTCUSDT`) существует и в spot, и в linear с разной ценой — агент, не глядя в спеку, может решить, что цена одна на всю биржу. → **Митигация:** описания всех инструментов явно говорят "только спотовый рынок Bybit", а не "Bybit" вообще; в будущем изменении с деривативами придётся ввести обязательный параметр категории — сейчас это осознанно отложено, т.к. категория всего одна.
- **[Риск]** Оценка "ожидаемое число свечей" для отказа на слишком большой период (без похода в сеть) может разойтись с реальностью на пограничных интервалах Bybit (например утренний/вечерний сдвиг границ дня в разных биржевых конвенциях). → **Митигация:** оценка намеренно консервативна (округление в большую сторону), возможная ложная ошибка "слишком большой период" безопаснее, чем зависший запрос на тысячи страниц.
- **[Риск]** У `search_symbols` весь справочник spot-пар (~2000+) кэшируется в памяти процесса; сервер запускается заново на каждое обращение клиента (как в mcp-moex), так что кэш редко переиспользуется между вызовами одного диалога. → **Компромисс принят:** соответствует модели mcp-moex (клиент — родитель процесса stdio), не меняем её ради кэша, который помогает только при долгоживущем процессе (streamable-http для отладки).
- **[Trade-off]** Отказ от прямой пробрасывания всех 13 кодов интервалов Bybit упрощает схему, но не даёт агенту гибкости (например 3-минутные свечи). Осознанно: это read-only аналитический сервер, а не терминал трейдера.

## Migration Plan

Greenfield-проект, миграции данных нет. Порядок реализации (детали — в `tasks.md`):
1. Скелет пакета, `pyproject.toml` (по образцу `mcp-moex`, имя `mcp-bybit`, entry point `mcp-bybit = "mcp_bybit.server:main"`).
2. `errors.py`, `bybit.py` (клиент + тесты на записанных фикстурах, сеть запрещена в тестах — тот же подход, что `tests/fixtures/` и `RECORD_FIXTURES=1` в mcp-moex, но с фикстурами Bybit).
3. `resolver.py`, `tools/search.py`, `models.py` для поиска.
4. `tools/price.py`.
5. `tools/history.py` (включая пагинацию).
6. Перенос `analytics/*` с правками из раздела Decisions, `tools/analytics.py`.
7. `server.py`, CLI, `scripts/smoke_client.py`, README.
8. Прогон `scripts/smoke_client.py` против реального Bybit перед тем, как считать реализацию готовой.

Отката не требуется (новый проект); в случае проблем с публикацией просто не выпускать пакет.
